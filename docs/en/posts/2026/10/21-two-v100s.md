# Deploying Strata and KVMem on Two V100 GPUs

<!-- DESC SEP -->

Two 16GB V100s can still be used to explore local inference, with attention to build targets and memory budgets. I deployed Strata and KVMem + NInfer separately. The latter retrieved three codes from nearly 256K input tokens, but the first request took almost 16 minutes and image recognition failed.

<!-- DESC SEP -->

On October 21, 2026, I ran Qwen3.8-Flash-Next IQ2_XS with [Strata](https://github.com/Niko1221/Strata) and Qwen3.8-27B with [KVMem](https://github.com/kvmem/kvmem) and [NInfer](https://github.com/iamwavecut/ninfer-all). The latter passed a retrieval test with nearly 256K tokens of input and one follow-up request.

Each setup uses both GPUs, so run one at a time. After preparing the host, choose either route.

## Prepare the Environment

I used the following host. A Windows virtual machine was also running during the experiments.

| Component | Configuration |
| --- | --- |
| OS | Ubuntu 26.04.1 LTS, x86_64 |
| GPU | Two Tesla V100-SXM2-16GB cards |
| NVIDIA driver | 580.178.04 |
| CPU | Xeon E5-2686 v4, 18 cores and 36 threads |
| RAM and swap | About 30GiB visible to the OS, 8GiB swap |
| Storage | SSD rated at 512GB |
| Docker and Compose | Docker 29.8.1, Compose v5.5.1 |

Run the commands below in Bash as root, using `/srv/llm` as the working directory. Prepare an R580 driver according to the [V100 architecture support matrix](https://docs.nvidia.com/datacenter/tesla/drivers/latest/cuda-toolkit-driver-and-architecture-matrix.html), then install [Docker Engine and the Compose plugin](https://docs.docker.com/engine/install/ubuntu/) and the [NVIDIA Container Toolkit](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/install-guide.html). Check the environment before continuing.

```bash
nvidia-smi
docker --version
docker compose version
```

If GPU container support is not configured yet, run the following commands. Schedule downtime for existing containers before restarting Docker.

```bash
nvidia-ctk runtime configure --runtime=docker
systemctl restart docker
```

Install the download and request tools. Run Python tools through [uv](https://docs.astral.sh/uv/getting-started/installation/). Build dependencies stay inside the images, so the host does not need a separate [CUDA Toolkit](https://developer.nvidia.com/cuda-toolkit) installation.

```bash
apt-get update
apt-get install -y ca-certificates curl git jq openssl

curl -LsSf https://astral.sh/uv/install.sh | sh
export PATH="$HOME/.local/bin:$PATH"
uv --version

mkdir -p /srv/llm/models/qwen \
  /srv/llm/strata-build /srv/llm/strata-data \
  /srv/llm/kvmem-build /srv/llm/kvmem-data
cd /srv/llm
df -h /srv/llm
docker system df
```

The two sets of model weights total about 88.5GB. Allow additional space for source code, images, and caches. Downloads require access to [GitHub](https://github.com/), [Hugging Face](https://huggingface.co/), and [ModelScope](https://modelscope.cn/). The image references retain the mirrors used on this host, `docker.1ms.run` and `ghcr.1ms.run`.

Use the [CUDA 12.8.1 image](https://hub.docker.com/r/nvidia/cuda) to check that containers can see both GPUs.

```bash
docker pull docker.1ms.run/nvidia/cuda:12.8.1-runtime-ubuntu24.04
docker run --rm --gpus all \
  docker.1ms.run/nvidia/cuda:12.8.1-runtime-ubuntu24.04 nvidia-smi
```

The output should list both V100 cards. Resolve any GPU container issues before continuing.

Download both IQ2_XS shards from the [ISTA-DASLab model repository](https://huggingface.co/ISTA-DASLab/Qwen3.8-Flash-Next-GSQ-RCO-GGUF), pinned to the revision recorded on this host. The [Hugging Face CLI](https://huggingface.co/docs/huggingface_hub/guides/cli#download-to-a-local-folder) preserves the repository directory structure with `--local-dir`.

```bash
uvx --from huggingface_hub hf download \
  ISTA-DASLab/Qwen3.8-Flash-Next-GSQ-RCO-GGUF \
  IQ2_XS/Qwen3.8-Flash-Next-GSQ-RCO-IQ2_XS-00001-of-00002.gguf \
  IQ2_XS/Qwen3.8-Flash-Next-GSQ-RCO-IQ2_XS-00002-of-00002.gguf \
  --revision ed59f92082b1e93c0e96d60a8b11aab089b52f09 \
  --local-dir /srv/llm/models/qwen/Qwen3.8-Flash-Next-GSQ-RCO
```

The shards are about 39.2GB and 28.8GB. The second contains the n-gram lookup table and is required. Keep both in the same directory with their original filenames. Image processing is disabled in this setup, so no `mmproj` download is needed.

```bash
ls -lh /srv/llm/models/qwen/Qwen3.8-Flash-Next-GSQ-RCO/IQ2_XS/
```

## Build the Strata Image

The Strata 0.2.1 CUDA 12 image I pulled lacked the `sm_70` target required by V100 and exited on startup. Rebuild it with CUDA 12.x and the experimental build option described in the [V100 build instructions](https://github.com/Niko1221/Strata/blob/a7bdbfdabc9a/docs/NVIDIA_V100.md).

Download and extract the pinned [Strata source](https://github.com/Niko1221/Strata/tree/a7bdbfdabc9a) and [llama.cpp dependency](https://github.com/ggml-org/llama.cpp/tree/3cf03257f219afbe7334045ff7c6a06ac68c627d).

```bash
cd /srv/llm/strata-build

curl -fL https://codeload.github.com/Niko1221/Strata/tar.gz/a7bdbfdabc9a \
  -o strata-a7bdbfdabc9a.tar.gz
mkdir -p Strata-a7bdbfdabc9a
tar -xzf strata-a7bdbfdabc9a.tar.gz \
  --strip-components=1 -C Strata-a7bdbfdabc9a

curl -fL \
  https://codeload.github.com/ggml-org/llama.cpp/tar.gz/3cf03257f219afbe7334045ff7c6a06ac68c627d \
  -o llama-3cf03257.tar.gz
mkdir -p Strata-a7bdbfdabc9a/third_party/llama.cpp
tar -xzf llama-3cf03257.tar.gz \
  --strip-components=1 -C Strata-a7bdbfdabc9a/third_party/llama.cpp
```

Save the following as `/srv/llm/strata-build/Dockerfile.v100`. The build reuses the CUDA 12.8 environment in the [1Cat-vLLM image](https://hub.docker.com/r/shig249/1cat-vllm-1.5.0), pins the image digests, and enables `sm_70` through the experimental option and architecture setting.

```dockerfile
FROM docker.1ms.run/shig249/1cat-vllm-1.5.0@sha256:013c033c7e088fe6d4eb95887d0a617eca4a38c73fa66423ec81fe3c4b90e576 AS build
WORKDIR /src
COPY Strata-a7bdbfdabc9a/ /src/
RUN cmake -G Ninja -S . -B /build \
      -DCMAKE_BUILD_TYPE=Release \
      -DSTRATA_ENABLE_CUDA=ON \
      -DSTRATA_EXPERIMENTAL_SM60=ON \
      -DSTRATA_BUILD_TESTS=OFF \
      -DSTRATA_PORTABLE=ON \
      -DCMAKE_CUDA_ARCHITECTURES=70 \
      -DSTRATA_GGML_DIR=/src/third_party/llama.cpp \
    && cmake --build /build --target strata strata_kq -j 6
RUN mkdir -p /stage \
    && cp /build/strata /build/libstrata_kq.so /src/LICENSE /stage/ \
    && uv run --no-project python packaging/collect_libs.py \
      --binary /build/strata --search /usr/local/cuda/lib64 \
      --out /stage --also 'libcublasLt.so*' \
    && uv run --no-project python packaging/package_engine.py \
      --src /stage --backend cuda --version 0.1.46 \
      --out /components/engine --arch sm_70 \
      --platform linux-x86_64 --variant cuda12-sm70 \
      --min-driver nvidia=575.51 \
      --build-id a7bdbfdabc9a-cuda12.8-sm70

FROM ghcr.1ms.run/niko1221/strata@sha256:e9b978fbf119ceddae7c1fd980a69e11bec96b149e33be77524b3601838c62d2
COPY --from=build /components/ /opt/strata-v100/components/
ENV STRATA_COMPONENTS_DIR=/opt/strata-v100/components
LABEL com.strata.engine="0.1.46-linux-x86_64-cuda-cuda12-sm70" \
      com.strata.build="a7bdbfdabc9a-cuda12.8-sm70"
```

The Dockerfile also collects CUDA shared libraries and packages the engine component. Build the image.

```bash
docker build --progress=plain \
  -f /srv/llm/strata-build/Dockerfile.v100 \
  -t local/strata:0.2.1-cuda12-sm70 /srv/llm/strata-build
```

## Start Strata

Save the following as `/srv/llm/docker-compose-strata-qwen3.8-flash-next.yml`. All APIs in this guide bind to `127.0.0.1` for checks on the host. Adjust both the binding and request addresses for LAN access.

```yaml
services:
  strata-qwen38-flash-next:
    image: local/strata:0.2.1-cuda12-sm70
    pull_policy: never
    container_name: strata-qwen38-flash-next
    restart: unless-stopped
    gpus: all
    ports:
      - '127.0.0.1:8080:8080'
    shm_size: 2gb
    stop_grace_period: 2m
    ulimits:
      memlock:
        soft: -1
        hard: -1
    volumes:
      - type: bind
        source: /srv/llm/models/qwen/Qwen3.8-Flash-Next-GSQ-RCO
        target: /models
        read_only: true
        bind:
          create_host_path: false
      - type: bind
        source: /srv/llm/strata-data
        target: /data
        bind:
          create_host_path: false
    environment:
      FAMILY: qwen
      STRATA_SOURCE: modelscope
      MODEL: IQ2_XS
      MODEL_PATH: /models/IQ2_XS/Qwen3.8-Flash-Next-GSQ-RCO-IQ2_XS-00001-of-00002.gguf
      GPUS: '0,1'
      CONTEXT: 32k
      PARALLEL: '1'
      VISION: 'off'
      KV: int8
      TUNE: skip
      STRATA_SET: >-
        vram-reserve-mib=1024 vram-reserve-later-mib=1046
        resident-budget-gib=16 STRATA_ROUTE_TAIL_SKIP=0
      PRESET: docker
```

This configuration splits layers across both GPUs, with a 32K context, one concurrent request, and INT8 KV. The host expert residency budget is 16GiB; the remaining experts are read from files on demand. `STRATA_SOURCE=modelscope` selects the source for MTP and other resources.

Stop any inference service using the GPUs, then check the configuration and start Strata.

```bash
nvidia-smi
docker compose -f /srv/llm/docker-compose-strata-qwen3.8-flash-next.yml \
  config --quiet
docker compose -f /srv/llm/docker-compose-strata-qwen3.8-flash-next.yml \
  up -d
docker logs -f --tail 100 strata-qwen38-flash-next
```

The first launch prepares pack and MTP resources. Press `Ctrl+C` to stop following the logs, then check the health endpoint. Wait for `loaded=true` before sending a request. Subsequent reloads took about two to three minutes on this host.

```bash
curl --noproxy '*' --fail-with-body -sS http://127.0.0.1:8080/health
docker exec strata-qwen38-flash-next \
  strata launch --show-key --preset docker
```

The second command displays the automatically generated, persisted API key. Copy it into the prompt below and send a short request.

```bash
read -r -s -p 'Strata API Key ' STRATA_API_KEY
printf '\n'

curl --noproxy '*' --fail-with-body -sS \
  http://127.0.0.1:8080/v1/chat/completions \
  -H "Authorization: Bearer $STRATA_API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "qwen3.8-flash-next-iq2_xs",
    "messages": [{"role": "user", "content": "Explain database transaction atomicity in one sentence."}],
    "max_tokens": 1024,
    "stream": false
  }' | jq .
```

Stop Strata to release both GPUs before switching to KVMem.

```bash
docker compose -f /srv/llm/docker-compose-strata-qwen3.8-flash-next.yml \
  stop
nvidia-smi
```

## Build the KVMem Image

Use the pinned [KVMem commit](https://github.com/kvmem/kvmem/commit/61569ff4bddcad60e8fad838e02f77a6190126d1) and [NInfer commit](https://github.com/iamwavecut/ninfer-all/commit/08fd7019925f43b4b42539400afd461b70f7144a). Run the [backend preparation script](https://github.com/kvmem/kvmem/blob/61569ff4bddcad60e8fad838e02f77a6190126d1/scripts/prepare-backends.py) to fetch the submodule and apply the integration patch before building.

```bash
cd /srv/llm/kvmem-build
git clone https://github.com/kvmem/kvmem.git src
git -C src checkout 61569ff4bddcad60e8fad838e02f77a6190126d1

uv run --no-project python src/scripts/prepare-backends.py --backend ninfer
uv run --no-project python src/scripts/prepare-backends.py \
  --backend ninfer --check
git -C src/backends/ninfer rev-parse HEAD
```

The check should report `ninfer: 08fd7019925f + ninfer-kvmem.patch ready`. The patch leaves the submodule marked as modified. Keep those changes.

Save the following as `/srv/llm/kvmem-build/Dockerfile`. It uses CUDA 12.8.1, Ubuntu 24.04, and GCC 13, with explicit settings for `sm_70` and the KVMem source path.

```dockerfile
FROM docker.1ms.run/nvidia/cuda:12.8.1-devel-ubuntu24.04 AS build
ENV DEBIAN_FRONTEND=noninteractive
RUN apt-get update && apt-get install -y --no-install-recommends \
      gcc-13 g++-13 cmake ninja-build pkg-config git \
      libavcodec-dev libavformat-dev libavutil-dev libswscale-dev \
      libcurl4-openssl-dev \
    && rm -rf /var/lib/apt/lists/*
WORKDIR /src
COPY src/ /src/
RUN cmake -S backends/ninfer -B /build -G Ninja \
      -DCMAKE_BUILD_TYPE=Release \
      -DCMAKE_C_COMPILER=gcc-13 \
      -DCMAKE_CXX_COMPILER=g++-13 \
      -DCMAKE_CUDA_HOST_COMPILER=g++-13 \
      -DCMAKE_CUDA_ARCHITECTURES=70 \
      -DNINFER_KVMEM_SOURCE_DIR=/src/kvmem \
      -DNINFER_BUILD_APPS=ON \
      -DNINFER_BUILD_BENCHMARKS=OFF \
      -DBUILD_TESTING=OFF \
    && cmake --build /build --target ninfer-serve --parallel 6

FROM docker.1ms.run/nvidia/cuda:12.8.1-runtime-ubuntu24.04
ENV DEBIAN_FRONTEND=noninteractive
RUN apt-get update && apt-get install -y --no-install-recommends \
      ca-certificates curl libavcodec60 libavformat60 libavutil58 \
      libswscale7 libcurl4t64 libgomp1 \
    && rm -rf /var/lib/apt/lists/*
COPY --from=build /build/apps/ninfer-serve /usr/local/bin/ninfer-serve
LABEL org.opencontainers.image.source="https://github.com/kvmem/kvmem" \
      org.opencontainers.image.revision="61569ff4bddcad60e8fad838e02f77a6190126d1" \
      local.ninfer.revision="08fd7019925f43b4b42539400afd461b70f7144a" \
      local.cuda.arch="sm_70"
ENV NVIDIA_VISIBLE_DEVICES=all NVIDIA_DRIVER_CAPABILITIES=compute,utility
ENTRYPOINT ["/usr/local/bin/ninfer-serve"]
```

Build the local image.

```bash
docker build --progress=plain \
  -f /srv/llm/kvmem-build/Dockerfile \
  -t local/kvmem-ninfer:sm70-61569ff4 /srv/llm/kvmem-build
```

## Start KVMem

Create the API key environment file on the first deployment. Reuse it afterward; running these commands again replaces the key.

```bash
cd /srv/llm
umask 077
printf 'NINFER_API_KEY=%s\n' "$(openssl rand -hex 32)" > kvmem-ninfer.env
chmod 600 kvmem-ninfer.env
```

Save the following as `/srv/llm/docker-compose-kvmem-qwen3.8-27b.yml`. It uses the configuration that passed the long-context retrieval test.

```yaml
services:
  kvmem-qwen38-27b:
    image: local/kvmem-ninfer:sm70-61569ff4
    pull_policy: never
    container_name: kvmem-qwen38-27b
    restart: 'no'
    gpus: all
    ports:
      - '127.0.0.1:18200:18200'
    shm_size: 2gb
    stop_grace_period: 2m
    ulimits:
      memlock:
        soft: -1
        hard: -1
    environment:
      CUDA_DEVICE_ORDER: PCI_BUS_ID
    volumes:
      - type: bind
        source: /srv/llm/models/qwen/Qwen3.8-27B-NInfer
        target: /models
        read_only: true
        bind:
          create_host_path: false
      - type: bind
        source: /srv/llm/kvmem-data
        target: /data
        bind:
          create_host_path: false
    command: >-
      /models/qwen3_8_27b.ninfer
      --host 0.0.0.0 --port 18200
      --api-key "${NINFER_API_KEY:?Set NINFER_API_KEY in the environment file}"
      --model-id qwen3.8-27b-kvmem --devices 0,1
      --max-context 262144 --max-concurrency 1
      --kv-dtype int8 --prefill-chunk 512
      --default-max-tokens 8192 --default-thinking-budget 4096
      --kvmem --kvmem-budget 253952 --kvmem-gen-reserve 8192
      --kvmem-host-mib 12288 --kvmem-sessions 1
      --kvmem-sink-tokens 4096 --kvmem-recent-tokens 1024
      --kvmem-lrfu --kvmem-lrfu-lambda 0.5
      --kvmem-lrfu-top-frac 0.9 --kvmem-score-agg max
      --vision --vision-residency cpu --vision-max-merged 1024
      --spec mtp --draft-tokens 2 --ngram-draft-tokens 0
```

This configuration uses a layer split across two GPUs, INT8 KV, one concurrent request, MTP with two draft tokens, and CPU vision encoding. The key budgets are listed below; their definitions are in the pinned [KVMem usage guide](https://github.com/kvmem/kvmem/blob/61569ff4bddcad60e8fad838e02f77a6190126d1/README.zh-CN.md).

| Parameter | Value and meaning |
| --- | --- |
| `max-context` | 262144 tokens shared by input, images, and output |
| `kvmem-budget` | 253952 tokens for the history budget B |
| `kvmem-gen-reserve` | 8192 tokens for the append workspace budget R, configured separately from API `max_tokens` |
| `kvmem-host-mib` | 12288MiB for native KV payload, not a limit on total process memory |

This version requires `B + R <= max-context`. The configuration does not enable the SSD KV tier and requires a manual start after a host reboot. Always pass the environment file when using this Compose file.

```bash
nvidia-smi
docker compose --env-file /srv/llm/kvmem-ninfer.env \
  -f /srv/llm/docker-compose-kvmem-qwen3.8-27b.yml config --quiet
docker compose --env-file /srv/llm/kvmem-ninfer.env \
  -f /srv/llm/docker-compose-kvmem-qwen3.8-27b.yml up -d
docker logs -f --tail 100 kvmem-qwen38-27b
```

Loading and warmup took about 47 seconds on this host. Stop following the logs and wait for the health endpoint to return HTTP 200 before sending a short request.

```bash
curl --noproxy '*' --fail-with-body -sS -o /dev/null \
  -w '%{http_code}\n' http://127.0.0.1:18200/health

set -a
. /srv/llm/kvmem-ninfer.env
set +a

curl --noproxy '*' --fail-with-body -sS \
  http://127.0.0.1:18200/v1/chat/completions \
  -H "Authorization: Bearer $NINFER_API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "qwen3.8-27b-kvmem",
    "messages": [{"role": "user", "content": "Explain database transaction atomicity in two sentences."}],
    "max_tokens": 256,
    "reasoning_effort": "none",
    "stream": false
  }' | jq .
```

`reasoning_effort: "none"` disables thinking. I also verified that `"low"` returns both reasoning and a final answer. The output budget must cover both, or the response may be truncated with `finish_reason=length`.

## Verify Tool Calls

Define an addition tool and check whether the model generates the expected call arguments.

```bash
curl --noproxy '*' --fail-with-body -sS \
  http://127.0.0.1:18200/v1/chat/completions \
  -H "Authorization: Bearer $NINFER_API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "qwen3.8-27b-kvmem",
    "messages": [{"role": "user", "content": "Call the sum tool to add 57 and 65."}],
    "tools": [{
      "type": "function",
      "function": {
        "name": "sum",
        "description": "Add two integers",
        "parameters": {
          "type": "object",
          "properties": {"a": {"type": "integer"}, "b": {"type": "integer"}},
          "required": ["a", "b"]
        }
      }
    }],
    "max_tokens": 512,
    "reasoning_effort": "none",
    "stream": false
  }' > /srv/llm/tool-call.json

jq '.choices[0].message' /srv/llm/tool-call.json
```

Check the tool name and arguments in `tool_calls`. Use [jq](https://jqlang.org/manual/) to calculate the result, preserve the original assistant message and call ID, and return the result in a `tool` message.

```bash
jq '{
  model: "qwen3.8-27b-kvmem",
  messages: [
    {role: "user", content: "Call the sum tool to add 57 and 65."},
    .choices[0].message,
    (.choices[0].message.tool_calls[0] | {
      role: "tool",
      tool_call_id: .id,
      content: (.function.arguments | fromjson | (.a + .b) | tostring)
    })
  ],
  max_tokens: 256,
  reasoning_effort: "none",
  stream: false
}' /srv/llm/tool-call.json > /srv/llm/tool-result-request.json

curl --noproxy '*' --fail-with-body -sS \
  http://127.0.0.1:18200/v1/chat/completions \
  -H "Authorization: Bearer $NINFER_API_KEY" \
  -H 'Content-Type: application/json' \
  --data-binary @/srv/llm/tool-result-request.json | jq .
```

The final answer should be 122. The full round trip passed in this experiment.

## Verify Long Context Retrieval

Prepare `/srv/llm/archive.txt` with project names and verification codes for ORION, LYRA, and VEGA near the beginning, middle, and end. Record the expected answers. Start with a short document, then increase the input length. Check `usage.prompt_tokens` for the actual token count and leave room for output.

Build the request with jq to avoid escaping the document by hand.

```bash
jq -n --rawfile archive /srv/llm/archive.txt '{
  model: "qwen3.8-27b-kvmem",
  messages: [{
    role: "user",
    content: ($archive + "\nFind the verification codes for ORION, LYRA, and VEGA in the archive. Answer each separately.")
  }],
  max_tokens: 512,
  reasoning_effort: "none",
  stream: false
}' > /srv/llm/long-request.json

curl --noproxy '*' --fail-with-body -sS \
  http://127.0.0.1:18200/v1/chat/completions \
  -H "Authorization: Bearer $NINFER_API_KEY" \
  -H 'Content-Type: application/json' \
  --data-binary @/srv/llm/long-request.json \
  -o /srv/llm/long-response.json \
  -w 'total_seconds=%{time_total}\n'

jq '{message: .choices[0].message, usage: .usage}' /srv/llm/long-response.json
```

## Results and Limits

With 259489 input tokens, the initial configuration with a smaller history budget missed two targets. After increasing the budget and adopting the current configuration, all three were found.

| History budget B | ORION | LYRA | VEGA | Time to first token |
| --- | --- | --- | --- | --- |
| 32768 tokens | Not found | Not found | Correct | About 465.8 seconds |
| 253952 tokens | Correct | Correct | Correct | About 945.8 seconds |

Other settings changed between runs, so the difference cannot be attributed entirely to the history budget. Finding all three codes establishes successful retrieval for this input, not accurate handling of arbitrary 256K-token documents.

The first retrieval request with the final configuration took about 946.8 seconds in total. I then kept the same message prefix and asked for the previously unqueried CYGNUS verification code, attaching an image as well. Of the 259886 input tokens, 259532 were reused from cache. The text answer was correct, and the request took about 12.1 seconds. Because the requests differed, their durations do not give a direct cache speedup ratio. Inspect `usage.prompt_tokens_details.cached_tokens` when reproducing the test.

OCR did not pass: the image showed 4729, but the model repeatedly returned 4720. A comparison using GPU-resident vision failed during startup with a duplicate parameter declaration for `vision/patch_embedding`, so the current setup keeps vision encoding on the CPU. Other long documents and sustained multi-turn use remain untested. [This pinned NInfer KVMem version](https://github.com/kvmem/kvmem/blob/61569ff4bddcad60e8fad838e02f77a6190126d1/README.zh-CN.md#多卡与并发) does not support video.

Resource observations are listed below. Available RAM and swap usage reflect the whole host, including the Windows virtual machine.

| Setup | GPU memory usage | Available host RAM | Swap usage |
| --- | --- | --- | --- |
| Strata while running | About 15.1GiB per GPU | About 4GiB | About 4GiB |
| Final KVMem configuration | About 13.0GiB and 13.4GiB after startup | About 8.9GiB after the long request | About 1.5GiB after the long request |

Strata passed short responses, a tool round trip, and a reasoning task. Long inputs and images have not been tested systematically. Two short requests generated about 45 and 106 tokens/s respectively. They used different inputs and outputs, and each number comes from a single observation.

## Troubleshoot and Switch Services

If startup fails, check the logs, GPU usage, image tags, mount paths, and environment file. Recheck answers after changing the budgets.

```bash
docker ps -a
nvidia-smi
free -h
docker logs --tail 100 kvmem-qwen38-27b
```

Stop KVMem before starting Strata with the earlier commands. Keep the data directories, local images, and build materials for future rebuilds.

```bash
docker compose --env-file /srv/llm/kvmem-ninfer.env \
  -f /srv/llm/docker-compose-kvmem-qwen3.8-27b.yml stop
```
