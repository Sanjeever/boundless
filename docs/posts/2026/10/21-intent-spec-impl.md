# 意图与代码

<!-- DESC SEP -->

AI 可以加快实现，从想法到可用软件，仍需把目标、要求与验收逐步对齐。借一个报表导出例子，聊聊 Intent、Spec 与 Impl。

<!-- DESC SEP -->

假设我要让 AI 给报表加个导出。

按钮很快出现，点击也能下载文件。打开一看，却只有当前页数据。我想在月底核对销售额，需要导出全部筛选结果，包括后面几页。

程序能运行，功能也像模像样，交付结果却仍然偏离预期。理解这类问题，可以借助三个概念，Intent、Spec 和 Impl。

Intent 本身就是完整单词，中文可译为“意图”。[《剑桥词典》](https://dictionary.cambridge.org/dictionary/english/intent)将其名词含义解释为想要并打算做某件事。放到软件开发中，本文用它表达想达成什么目标、解决什么问题。在报表例子里，这个目标是核对月底销售额，减少手工整理。导出文件是其中一种手段。

Spec 是 Specification 简写，中文常译为“规格”或“规约”。[《剑桥词典》](https://dictionary.cambridge.org/dictionary/english/specification)将其解释为对某事应当怎样完成或制造作出详细描述，并注明 spec 属于非正式简称。在本文语境中，Spec 把目标转成具体行为与约束。例如，导出当前筛选条件下全部明细，金额保留两位小数，合计与报表一致。这些要求需要具体到能够检查结果。

这里用 Impl 表示 Implementation，中文译为“实现”。[《剑桥词典》](https://dictionary.cambridge.org/us/dictionary/english/implementation)将其解释为把计划付诸行动，或开始使用某项计划、系统。在软件开发中，Impl 也常指落实规格后产出，比如代码、配置与数据处理流程。例如，复用筛选查询，处理分页，生成文件，再提供下载。不同代码和技术方案，可以满足同一份规格。

顺着软件形成过程，可以写成 `Intent → Spec → Impl`。目标逐渐变成明确要求，再变成可运行程序。

[jyy《生成式软件工程》课程讲义](https://jyywiki.cn/GSE/2026/lect1.md)讨论过三者之间存在缺口。每个箭头都包含选择，也可能引入偏差。

从 Intent 到 Spec，需要把目标转成要求。如果把“方便核对销售额”理解成“下载一个文件”，规格就可能遗漏数据范围与汇总口径。即使代码逐条满足规格，用户仍然要来回翻页、手工拼接。

从 Spec 到 Impl，需要把要求变成可执行程序。如果规格已经写明“全部明细”，代码却沿用列表接口默认分页，偏差就发生在实现阶段。

这两类问题需要不同处理。前者要补充或修正规格，后者要修改实现。遇到结果不符合预期，先辨认偏差发生在哪一步，通常比继续追加一句“再改改”更有用。

在 Vibe Coding 中，AI 可以很快填补空白。我们省略数据范围，它可能沿用分页；我们没说金额精度，它可能自行选择。每次选择看起来都合理，组合起来却可能偏离目标。

所以，交给 AI 一项任务时，值得多说几句。

先说用途。例如，“月底我要核对销售额，希望减少逐页复制”。再让 AI 整理关键行为、约束、验收例子，列出哪些事项需要确认，哪些需要试验。双方确认关键取舍后，再进入实现。

[GitHub 官方介绍 Spec Kit 时](https://github.blog/ai-and-ml/generative-ai/spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/)强调，规格应持续指导规划、实现与验证，并随项目演进更新。这个思路也适用于小任务。用一段文字写清要求和验收方式，保留记录，后续修改时就有依据。

规格也可以逐步形成。拿不准交互时，先做小原型；试用后发现遗漏，再更新要求。AI 能帮助澄清意图、起草规格、执行检查，人需要确认关键取舍，并判断结果是否有用。

验收时，两端都要看。文件是否包含全部明细，可以通过检查验证；拿到文件后能否顺利核对销售额，还要回到真实场景。测试通过，说明程序通过当前检查，检查本身也可能遗漏需求。

下次给 Coding Agent 下任务，可以先问三句。

> 我想解决什么问题？
> 什么结果算完成？
> 用什么证据确认？

生成代码越容易，越值得把目标、要求与验收说清楚。
