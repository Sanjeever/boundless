# 代码变了，文档怎么办

<!-- DESC SEP -->

一次实现符合要求，后续修改仍可能让代码、规格与文档逐渐分开。我会让 Coding Agent 整理已有文档，再把基于语义变化的增量维护写进 AGENTS.md，为下一次会话留下可靠的项目知识。

<!-- DESC SEP -->

上一篇[《意图与代码》](/posts/2026/10/21-intent-spec-impl)聊过 `Intent → Spec → Impl`。目标变成可检查的要求，再变成可运行的程序，每一步都可能出现偏差。

假设报表导出已经正确实现，能够下载全部筛选结果。项目继续开发，数据量越来越大，导出改为后台任务：先提交请求，拿到任务 ID，等文件生成后再下载。

代码改好了，README 却仍写着“请求成功后直接返回文件”，示例也继续把响应当作文件保存。新会话里的 Coding Agent 读到示例，准备给另一个页面接入导出。它照着写，得到的可能是一个装着任务 ID 的“报表文件”。

这个例子是假设，但它说明文档过时怎样进入后续实现。旧说明看起来有据可依，错误便有机会沿着下一次任务继续传播。

我把这种代码演进与已有说明逐渐分开的情况称为 **Documentation Drift，文档漂移**。它可能出现在 README、设计文档，也可能藏在代码注释、示例和配置说明里。对长期使用 Coding Agent 开发的项目，我尤其在意它：新会话需要重新获取上下文，我们留下什么，会参与它下一次判断。

所以，我一般会给 Agent 一项专门的文档维护任务。整理已经积累的问题，同时把后续维护原则写进 AGENTS.md。这里面最需要说清楚的，是发生冲突时如何判断。

## 先判断，这件事应该听谁的

“让文档与代码保持一致”听起来很合理，执行起来却可能把问题藏住。

仍然用导出举例。如果文档说接口同步返回文件，当前实现已经经过确认改成异步任务，那么旧操作说明需要更新。可如果规格写着“导出全部筛选结果”，代码只导出当前页，直接把文档改成“导出当前页”，就把一个可能的缺陷写成了新要求。

两个冲突都表现为文字与代码不一致，需要处理的方向却不同。

这里需要明确 **Source of Truth，事实来源**。我会先根据内容性质区分依据。

| 要回答的问题                             | 主要依据                                      |
| ---------------------------------------- | --------------------------------------------- |
| 当前内部调用什么函数、采用什么数据结构？ | 实现代码                                      |
| 当前配置默认值是什么，接口实际怎样响应？ | 配置定义、实现及能验证相应行为的测试          |
| 接口应该接受什么输入、提供什么保证？     | 已确认的契约或 Schema，以及相应实现和契约测试 |
| 系统为什么这样设计，哪些边界应当保持？   | 已确认的规格、设计文档、架构决策记录          |
| 用户应该怎样运行、使用和部署？           | 与实际流程核对过的操作说明                    |

表里的依据也需要核对。Schema 如果没有参与校验，可能与实际接口分开；测试如果断言写错，也会认可错误行为。某份设计文档是否仍有效，要看它记录的决策状态和后续变更。

**代码能说明当前实现了什么，既定约束则参与判断这样实现是否正确。** 两者发生冲突时，需要追查原有理由、需求变更和相关证据。有依据的设计调整应更新说明；未经确认的行为偏差需要修复。重大取舍无法从仓库判断，就把分歧交给有决策权的人。

Michael Nygard 在 [《Documenting Architecture Decisions》](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions)里讨论过接手者的困境：不知道过去的理由，容易盲目接受，也容易盲目推翻。他提出用 ADR（Architecture Decision Record，架构决策记录）保留背景、决定、状态与后果；决定被取代后，保留旧记录并标记替代关系。

这也是我要求 Agent 保留设计背景的原因。一次整理如果把文档全部改成当前代码的样子，可能连判断代码是否偏离要求的依据都一起抹掉。

## 少留一些需要反复同步的事实

明确依据之后，还要减少重复维护。

《程序员修炼之道》的 [DRY 原则](https://pragprog.com/tips/)要求，每一项知识在系统中应有单一、明确、权威的表示。这个原则涉及知识重复，也适合检查文档。

假设重试次数的默认值在代码、README、配置示例和 AGENTS.md 中各写一遍。改默认值时，需要找齐四处；漏掉一处，读者就可能得到不同答案。我更愿意让配置定义承担默认值的依据，参考文档说明选项含义，其他入口指向它。确实需要展示数值的示例，则需要进入相关变更的影响检查。

还有一类内容可以直接减少。

```diff
- TaskQueue 使用 LinkedList 保存任务。
+ TaskQueue 负责维护待执行任务的有序队列。
```

如果读者只需要理解模块职责，后一句就足够。内部换了数据结构，职责可能仍然成立，文档也无需跟着改。

但如果数据结构关系到重要约束，删除细节同样可能损失信息。比如一个假设中的队列需要频繁取消任意位置的任务，选择数据结构时考虑过删除成本。此时值得记录取消需求、成本要求及选择理由。将来操作模式发生变化，接手者才能判断是否需要重新评估。

[Google 的代码审查指南](https://google.github.io/eng-practices/review/reviewer/looking-for.html#comments)也区分了这两类说明：注释通常应补充代码无法直接表达的理由；类、模块与函数文档还需要说明用途、用法和行为。

因此，“少重复实现细节”不能扩大成“文档都只写 Why”。API 的输入、输出、错误语义，配置项的含义，部署的必要步骤，都值得具体写。要检查的是，这些信息服务什么读者，应该在哪里维护，以及变化后怎样发现它受了影响。

## README、docs 和 AGENTS.md 各自做什么

文档职责混在一起，也会增加重复。

我倾向于让 README 保持入口性质。读者能知道项目是什么、核心能力有哪些、怎样运行和参与开发，再沿链接找到详细资料。某个类怎样组装、内部函数怎样调用，通常不需要挤在入口里。

[Diátaxis](https://diataxis.fr/)按读者需要区分教程、操作指南、技术参考和解释。这给整理文档提供了一个实用视角：读者正在学习、完成任务、查准确资料，还是理解设计？

放到导出功能里，接入一个最小示例、查阅任务状态字段、理解为什么采用异步任务，是不同的阅读需要。它们可以互相链接。是否拆成独立文件，要看篇幅和实际查找成本，小项目用一篇文档的几个章节也可以。

至于 AGENTS.md，[官方说明](https://agents.md/#why-agents-md)把它作为向 Coding Agent 提供项目上下文和工作指引的固定入口，补充面向人的 README。

在我这套做法里，它还要说明处理文档影响的原则。Agent 需要知道哪些约束应当遵守、去哪里找依据，以及什么结果算完成。详细设计已经有专门文档，就链接过去；反复复制，会让 AGENTS.md 也成为另一个需要追赶实现的副本。

## 先整理存量，再约束后续修改

当项目已经积累一批过时文档，我会让 Agent 做一次集中整理。范围包括 README、docs、AGENTS.md、注释、示例和配置说明，重点检查重复、过时、矛盾及缺失的设计理由。

这里要求“全面审查”，是为了处理存量。Agent 要阅读材料，通过代码、测试和配置验证重要事实，再决定删除、合并、改写还是保留。已有结构足够清楚，就沿用；整理出几个问题，也无需因此重新设计整个文档目录。

我会把两项要求一起交给它：减少易腐的实现描述，保留有长期价值的约束与决策背景。前者避免文档追着局部实现跑，后者防止整理变成删光细节。

不过，一次整理完成，只能说明当时处理过这些问题。下一个功能仍然可能改接口、换配置、调整部署方式，留下新的偏差。因此，我还会要求 Agent 在 AGENTS.md 中写入后续任务适用的原则。

例如，下面这段可以作为起点，再按项目实际情况调整。

```text
文档一致性

当前实现细节以代码为依据；明确的架构约束、设计决策和行为契约，
以已确认的设计材料为依据。两者冲突时，结合变更背景解决分歧。

完成有语义影响的修改时：
- 理解最终改动改变了什么行为、接口、约束、架构或实现假设。
- 查找可能描述这些内容的文档、注释、测试、示例和配置。
- 更新会因此失实、误导读者或产生矛盾的内容。
- 文档是否需要修改，取决于语义影响，而非源文件是否发生变化。
- 优先保留稳定概念、行为、边界、约束及其理由。

检查范围与任务影响相称，无需每次阅读全部文档。
```

[Write the Docs 对 Docs as Code 的介绍](https://www.writethedocs.org/guide/docs-as-code/)强调，文档使用版本控制、代码审查等工具，并融入开发工作流。我希望把文档影响判断放进 Agent 的任务完成条件里，也是在落实这个方向。

Markdown 和代码放在同一个仓库，方便一起修改和审查。至于这次究竟该改哪几段，仍需要理解变化。

## 从语义变化找到受影响的知识

“这次改了导出服务”还不够具体。更有用的描述是：“导出接口从直接返回文件，改为返回任务 ID，调用方需要查询状态并在完成后下载。”

后一句包含了要找的线索。接口文档可能描述返回类型，前端示例可能假设拿到文件，操作说明可能写着“点击后立即下载”。即使这些地方没有出现服务类名，也已经受到影响。

这就是我说的 **Impact Analysis，影响分析**。在文档维护里，先理解变化，再寻找哪些已有知识依赖旧行为。我把据此定位任务所需资料的过程称为 **Context Routing**：根据问题选择阅读入口，逐步补齐上下文。

具体可以用 `git diff` 查看改动，用 `git status --short` 确认工作区范围，再用 `rg` 搜索接口路径、配置项、旧术语和行为描述。这些命令提供线索，实际操作应随任务调整。新文件还未加入 Git 时，也需要读它的内容，不能指望普通 diff 自动涵盖一切。

例如，在前面的假设项目里，可以这样寻找旧导出约定。

```bash
rg -n 'exportReport|/api/reports/export|直接返回文件|同步导出' .
```

搜索结果需要逐项判断。历史决策记录可能应该保留，当前接入示例则需要改写；有些说明用了不同措辞，还得沿调用方和文档入口继续找。命中同一个词，说明它值得查看，尚不足以决定修改。

几种看起来相近的任务，影响也可能不同。

| 本次变化                           | 需要追查的内容                                           |
| ---------------------------------- | -------------------------------------------------------- |
| 更换队列内部数据结构，行为保持一致 | 是否有实现描述过时，原有选择理由是否仍成立               |
| 同步导出改为异步任务               | 接口契约、调用示例、交互流程，以及相关超时与状态配置     |
| 导出范围从全部结果变成当前页       | 是否违背既定规格，需求变更是否有明确依据                 |
| 内部函数重命名                     | 文档是否确实引用该符号；纯内部重命名可能无需更新读者文档 |

理解需求时可以先做一轮影响分析，帮助找到实施所需资料；完成后，再基于最终变化检查，因为实际实现可能偏离最初计划。这个过程可以写成：

```text
识别拟改变的行为与约束
    → 寻找相关上下文
    → 实施修改
    → 根据最终变化检查一致性
```

[Google 审查指南的 Documentation 一节](https://google.github.io/eng-practices/review/reviewer/looking-for.html#documentation)给过具体判断：变更影响构建、测试、交互或发布方式时，应检查相关文档是否更新。这种以影响为入口的要求，比笼统说“记得同步文档”更容易落实。

我希望 Agent 在结束任务前，能够回答三件事。

> 本次改变了什么行为、接口、约束、架构或实现假设？
>
> 仓库里还有哪些地方描述这些内容？
>
> 当前代码、文档、测试、示例和配置，是否仍然一致？

这里说的一致，包括实现符合仍然有效的约束，也包括操作说明对应真实流程。文档没有变化，可能是因为本次修改没有影响它；文档改了很多，也可能遗漏最关键的契约。审查需要回到具体内容。

## 给下一次会话留下什么

项目较小时，清晰的入口、几个链接和上述约束通常就够。多个子系统让资料查找明显变困难后，可以再考虑轻量的代码—文档映射，例如将某组代码目录指向对应架构文档。映射也需要维护，只有节省的查找成本值得这份负担时，我才会添加。

最终 diff 值得再读一次。删掉的段落里是否藏着重要设计理由？移动文档后有没有留下两份默认值？写进 AGENTS.md 的要求，会不会让下一次小修改也必须跑完整套流程？整理过程本身也可能制造问题。

我还不能据此说，一份维护提示词就能消除文档漂移。Agent 可能漏查，也可能错误理解设计，重要分歧仍需人判断。我希望建立的是一个具体的工作要求：交付功能时，也检查它有没有让项目留下错误说明。

下一次会话不需要复原我们全部讨论，但它应当能找到当前要求、关键边界，以及做出这些选择的理由。

::: details 文档维护任务，可按项目调整后交给 Coding Agent

下面是按本文原则整理的任务版本。执行前，应先确认工作区中哪些改动属于已有工作。

```md
请审查并优化当前项目的文档体系，直接完成必要修改。

范围包括 README.md、`docs/**`、AGENTS.md、代码注释中的架构说明、
示例、配置说明、开发说明，以及其他具有长期维护价值的文本材料。

目标是减少 Documentation Drift，并让未来新的 Coding Agent 会话
能够找到可靠的项目知识。根据项目实际规模工作，保持简单。

## 先理解项目

阅读现有 AGENTS.md、README 和相关文档，了解主要代码目录与模块。
通过代码、配置和测试核对重要事实，查找明显重复、过时和矛盾的信息。

保留用户已有改动。不要仅凭文件名或搜索命中就删除、移动或改写内容。

## 判断事实来源

- 当前实现细节，以代码为依据。
- 配置项及默认值，以实际配置定义和代码为依据。
- API 实际行为，结合代码、Schema、测试及其实际校验范围判断。
- 行为契约、架构约束和设计决策，以已确认的规格与设计材料为依据。
- 用户操作与部署说明，需要与实际流程核对。

代码与文档冲突时，先判断文档是在描述当前实现，还是规定应当遵守的约束。
过时的实现描述可以修正；明确的设计约束不能因代码不同就直接删除。
结合变更记录、代码、测试和上下文，有依据地解决冲突。

无法从仓库判断的重大设计分歧，保留相关材料并在结果中指出。
继续完成不依赖该决策的工作。

## 减少重复与易腐信息

检查类名、方法名、内部调用和数据结构等描述是否确有阅读价值。
能够直接从代码获取、又不承担解释作用的内容，可以删除或改成稳定描述。

如果实现选择本身具有设计价值，保留背景、约束、理由与后果。
不要在精简时丢失这些依据。

优先让同一个易变事实在一处维护，其他位置通过链接引用。
需要展示具体行为、参数和步骤的参考文档与操作指南，应保持准确具体。

## 整理文档职责

README 主要提供项目介绍、核心能力、结构概览、运行与开发入口。
详细资料放到适合的位置，并保持链接可达。

处理 docs 中的重复、过时、职责不清和相互矛盾的问题。
已有结构足够好，就沿用。不要为了形式完整新增大量小文档。

历史决策与当前操作说明应能区分。已被替代但仍有价值的决策，
保留背景并明确其状态和替代关系。

## 为未来任务更新 AGENTS.md

按项目实际情况组织目标、原则、边界、事实来源与完成标准。
给 Agent 保留实现自主权，避免每次任务固定阅读全部文档、执行无关检查。

加入适合本项目的文档一致性原则：

- 有语义影响的修改完成后，理解最终变化涉及的行为、接口、约束、
  架构或实现假设。
- 查找可能描述这些内容的文档、注释、测试、示例和配置。
- 更新会因此失实、误导读者或相互矛盾的内容。
- 不因源文件发生变化就机械修改文档。
- 实现与明确的架构约束或设计决策冲突时，有依据地解决分歧。
- 优先记录稳定概念、行为、边界、约束和理由。
- 检查范围与任务影响相称。

可以使用 git diff、git status --short、rg 等工具，也可以自行选择方法。
重点是理解变化与知识之间的关系。

只有项目确实需要降低跨子系统的资料查找成本时，才添加轻量代码—文档映射。

## 完成与检查

采用与改动相称的验证。文档整理不要求机械运行全套构建或测试；
需要核对某个命令、配置或行为时，选择能提供相应证据的方法。

基于最终变更，包括新增和移动的文件，再做一次整体一致性检查：

1. 当前说明是否仍有明显过时或矛盾的内容？
2. 整理过程是否产生新的重复信息或失效链接？
3. 是否把仍有效的约束误改成当前实现？
```
