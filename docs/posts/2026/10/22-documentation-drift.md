# 代码变了，文档怎么办

<!-- DESC SEP -->

代码已经更新，旧说明却可能继续影响 Coding Agent 的下一次实现。怎样判断哪些说明已经失效，哪些约束仍应成立，是我维护项目文档时最在意的问题。

<!-- DESC SEP -->

假设一个报表接口原本直接返回文件，后来数据量增大，导出改为后台任务：先返回任务 ID，生成完成后再下载。代码已经更新，README 和接入示例还停在旧版本。下一次会话里，Coding Agent 照着示例开发新页面，就可能把任务 ID 保存成“报表文件”。

这种代码演进与已有说明逐渐分开的情况，就是 **Documentation Drift，文档漂移**。旧说明进入新会话的上下文，又参与下一次实现，错误便有机会继续传播。

## 文档错了，还是实现错了

“让文档与代码一致”也需要判断。如果后台任务方案已经确认，旧接入说明就应更新；可如果规格要求导出全部筛选结果，代码却只导出当前页，把文档改成“导出当前页”，就可能把缺陷写成新要求。

上一篇[《意图与代码》](/posts/2026/10/21-intent-spec-impl)讨论过 `Intent → Spec → Impl`。规格表达要求，实现给出具体行为。二者有分歧时，需要弄清哪些决定已经改变，哪些承诺仍然有效。

**代码能说明当前实现了什么，既定约束则参与判断这样实现是否正确。** 我会根据问题找依据：核对实际返回值，就查看实现和相应测试；判断导出范围是否正确，就追查已确认的规格及后续变更。测试和 Schema 也需要核对其检查范围，它们不会自动保证需求正确。

jyy 在[《软件工程的来龙去脉》](https://jyywiki.cn/GSE/2026/lect5.md)中区分了具体行为与行为必须满足的要求，也提醒我们保存尚未决定的部分。放到这里，Agent 为完成实现临时填入的选择，需要与已确认的要求区分。仓库无法解释的重大分歧，应保留材料，交给有决策权的人判断。

## 留下决定，也留下它成立的条件

要判断某个约束是否仍然适用，光知道当初选了什么还不够。

继续看导出。文档写着“采用后台任务”，接手者能知道当前方案；再写清数据量增长、同步请求耗时过长，以及仍需导出全部筛选结果，就能解释为什么采用这个方案、哪些要求没有因此改变。如果以后同步处理变得足够快，也有依据重新评估。

[《需求和架构（1）》](https://jyywiki.cn/GSE/2026/lect6.md)讨论过，一个当前结果可能压缩了事实、规则和审批过程。只留下结果，后面就难以解释它从哪里来。文档维护也有类似问题：把“为什么改成后台任务”删掉，再准确地复述当前代码，也补不回这项判断。

Michael Nygard 提出的 [ADR（架构决策记录）](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions)用于保留重要决定的背景、状态与后果。旧决定被替代后，保留记录并标明替代关系。具体项目未必需要专门建一套 ADR 目录，但决定及其适用前提应当有地方可查。

这也给精简文档划出边界。内部函数怎样调用，若没有额外解释价值，可以交给代码；某个选择承担了什么约束、牺牲了什么，则值得留下。否则，下次修改仍要重新猜一遍。

## 减少需要手工同步的信息

保留有价值的知识，还要控制维护它的成本。同一个接口返回类型在 README、参考文档、接入示例和 AGENTS.md 中各写一遍，修改时就多了几处可能遗漏的地方。

[《需求和架构（2）》](https://jyywiki.cn/GSE/2026/lect7.md)提供了一个值得借鉴的思路：保存事实与规则，让可以推导的结果由计算产生。这样，维护重点就能从多份状态的同步，转向计算及其依赖是否正确。

用于文档，我会先检查哪些重复信息有明确来源。例如，任务状态和响应字段若已有统一定义，可以据此生成参考说明；接入示例若能执行，可以纳入接口检查，发现它是否还在把响应当作文件保存。

但生成出来的参数表，仍可能准确描述一个不符合要求的接口。“必须导出全部筛选结果”这项承诺，以及采用后台任务的理由，都需要独立保存，作为判断实现的依据。

剩下的说明也应有清楚的归属。我倾向于让 README 提供运行与开发入口，详细文档保存契约、用法和设计背景，AGENTS.md 说明工作约束及资料入口。已有详细说明就链接过去，减少易变事实的副本。API 的输入输出、错误语义和部署步骤仍应具体，精简不能让读者失去完成任务所需的信息。

## 把相关说明纳入一次完整变更

即使减少了副本，一次修改仍然可能影响多个地方。要找到它们，需要先说清行为怎样变了。

“改了导出服务”只能指向一组代码；“接口从返回文件改为返回任务 ID，调用方需要查询状态并在完成后下载”，则给出了返回类型、状态查询和下载流程这些线索。接口契约、调用方、示例和操作说明，都可能依赖旧行为。

[《版本管理（2）》](https://jyywiki.cn/GSE/2026/lect4.md)把需求、设计、实现和验证之间的联系称为可追踪性。文件放在同一个仓库，Git 保存了它们的历史，也不会自动说明哪段示例依赖哪个契约。文档维护中的影响分析，就是在变化发生时沿着这些联系查找。

在前面的假设项目里，可以先搜索旧接口和旧说法。

```bash
rg -n 'exportReport|/api/reports/export|直接返回文件|同步导出' .
```

命中结果还要逐项判断：当前接入示例应改写，历史决策记录可能需要保留并标明已被替代。没有命中的说明，也可能用了另一种措辞，需要沿调用方和文档链接继续查看。检查应从拟改变的行为开始，完成后再对照最终改动核查，避免实际方案变化后仍按最初计划收尾。

[《版本管理》](https://jyywiki.cn/GSE/2026/lect3.md)讨论的原子变更，是围绕一个明确意图组织、能够解释和验证的完整修改。我希望文档也进入这个范围：后台任务实现完成时，相关契约、接入示例和操作说明一起接受审查，确认当前说明是否还让调用方依赖旧行为。

落实到 AGENTS.md，可以保留一段短规则。

```text
文档一致性

- 完成修改时，说明最终改变了什么行为、接口或约束，沿相关调用与
  文档入口，检查契约、示例、注释和操作说明是否仍然成立。
- 当前实现与已确认要求冲突时，结合需求和变更背景解决分歧，
  不将行为偏差直接改写为新要求。
- 保留重要决定及其理由，减少重复的易变事实。
- 检查范围与任务影响相称；文档是否需要改，取决于内容是否受影响。
```

如果已经积累了不少过时文档，我会先给 Agent 一项集中维护任务，核对重要事实，处理重复和矛盾，再把上述原则写进 AGENTS.md。已有结构足够清楚就沿用，也要检查整理过程是否误删了设计理由、留下失效链接。此后每次修改按影响检查，避免把集中清理变成日常任务的固定负担。

Agent 仍可能漏查或误解设计，重要分歧也需要人判断。这套做法能否减少后续误用，还要在持续修改中检验。

下一次会话不需要复原我们全部讨论，但它应当能找到当前要求、关键边界，以及做出这些选择的理由。
