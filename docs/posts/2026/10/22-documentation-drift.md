# 代码变了，文档怎么办

<!-- DESC SEP -->

当代码演进而旧文档留在原地，过时的说明就会把错误带进 Coding Agent 的下一次实现。

<!-- DESC SEP -->

设想一个报表接口最初直接返回文件流。后来数据量涨了十倍，导出改成了异步任务：接口先返回一个任务 ID，等后台生成完再去下载。

代码已经合并上线了，仓库里的 README 和调用示例却还停在半年前。到了下一次会话，Coding Agent 读完旧示例去写新页面，很自然地就把接口返回的那串任务 ID 当成报表文件存进了磁盘。

这就是常见的 **Documentation Drift（文档漂移）**。在人与 AI 协作频繁的项目里，一段过时的文档不只是让人看着别扭，它会直接混进下一次对话的上下文，成为新 Bug 的温床。

## 是文档旧了，还是代码写歪了

发现文档和代码对不上时，第一反应往往是“照着代码把文档改了”。但在此之前，最好先停下来问一句：到底是文档落后了，还是代码写漏了？

延续上一篇[《意图与代码》](/posts/2026/10/21-intent-spec-impl)里的例子：如果团队确实决定把同步导出改成异步任务，那更新接入文档天经地义；可如果需求明明写着“导出全部筛选结果”，代码却因为偷懒只导出了第一页，这时候顺手把文档改成“本接口仅导出当前页”，就等于把一个 Bug 追认成了正式需求。

正如 [jyy 在《软件工程的来龙去脉》](https://jyywiki.cn/GSE/2026/lect5.md)里提到的，**代码只说明当前实现了什么，而既定的规格约束才决定这样实现算不算对**。核对返回值格式时看代码和测试；判断业务边界有没有缩水时，得去翻最初确认的需求和变更记录。

## 记下决定，也记下当时的前提

只写“怎么做”的文档很容易过期，同时记下“当时为什么这么选”的文档却能耐看很久。

比如在导出模块旁留一句话：“因单次导出超过十万行时同步请求容易超时，改为后台任务；仍需保证导出全部筛选结果。”（这也是 [《需求和架构（1）》](https://jyywiki.cn/GSE/2026/lect6.md) 与 Michael Nygard 的 [ADR 架构决策记录](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions) 所看重的背景信息。）

有了这句话，半年后接手的人（或 Agent）一眼就能分清两件事：“用后台任务”是受限于当时性能的技术手段，而“导出全部筛选结果”是不能动摇的业务承诺。至于函数内部怎么调来调去，代码自己就能说清楚，不必在文档里复述一遍。

## 少留几份需要手工同步的副本

同一个接口的参数表，如果在 README、`docs/api.md`、代码示例和 `AGENTS.md` 里各抄了一遍，改代码时漏掉其中一两处几乎是必然的。

借用 [《需求和架构（2）》](https://jyywiki.cn/GSE/2026/lect7.md) 里的思路：尽量只存一份事实，能推导或引用的地方绝不手抄第二遍。

- **各司其职**：`README` 只管怎么跑起来；详细契约与设计背景放进 `docs/`；`AGENTS.md` 只写协作纪律和文档入口链接。
- **让示例可验证**：如果接入示例本身就是一段能跑的测试或脚本，接口一改，CI 就会先替你报警。

## 把文档检查收进同一次变更

改完一处行为后，顺着 [《版本管理（2）》](https://jyywiki.cn/GSE/2026/lect4.md) 说的可追踪性线索用 `rg` 扫一圈旧接口名和旧术语：

```bash
rg -n 'exportReport|/api/reports/export|直接返回文件|同步导出' .
```

把代码、测试和受影响的文档放在同一次提交里收尾（[原子变更](https://jyywiki.cn/GSE/2026/lect3.md)），远比攒到半年后做一次痛苦的“文档大扫除”轻松。

在项目的 `AGENTS.md` 里，只需留几行简短的约束：

```text
文档一致性
- 修改行为、接口或配置时，用 rg 检查受影响的文档、示例与注释并同步更新。
- 实现与既定需求冲突时，先核对需求背景，不把代码缺陷直接改写成文档规定。
- 记录重要决策的前提与取舍，减少同一事实在多处文档中的重复抄写。
```

下一次新会话开启时，Agent 不需要知道我们今天聊过的所有细节；它只需要打开仓库，就能找到干净的入口、仍然有效的约束，以及当初做出那些决定的理由。

```md
请审查并清理当前项目的文档（包括 README、docs、AGENTS.md、注释与示例）：

1. 对照当前代码、配置与测试核实文档中的事实，修正过时、重复或自相矛盾的说明。
2. 区分“有意演进的设计”与“实现偏离需求的缺陷”；遇到重大分歧时保留证据并向我确认，不要直接把 Bug 写成合法文档。

4. 减少同一易变事实在多处文档中的重复副本，改用链接指向唯一真身。
5. 在 AGENTS.md 中补充简短的文档同步规则，确保后续修改接口或行为时同步检查受影响的文档。
```
